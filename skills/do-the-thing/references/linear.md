# Linear interaction contract

This is an agent-operated integration through tools supplied by the host, not an installed Linear agent service. Tool names differ by host, so discover the available operations rather than inventing calls — and read the host's actual tool list rather than a document describing it. A widely installed third-party skill still lists `create_comment`, `create_issue`, and `update_issue` for the official Linear MCP; the server actually exposes `save_comment` and `save_issue`, where one call both creates and updates. A tool list you did not enumerate yourself is a guess.

What the host offers decides how much of this contract you can honour. Enumerate first, then choose the path, then say in the checkpoint which operations you had. A gateway that only creates and replaces issues can still run this workflow; it just cannot do the parts marked below as needing a specific capability.

1. Read viewer/workspace identity and the target issue, team, current status, relevant comments, and linked project or parent. Match the user's intended destination.
2. Locate an existing Big and Minis before creating records. Search the issue's actual relationships and stable spec markers, not titles alone.
3. Store a Big in a project-linked document when the host can write documents, otherwise in the parent issue body. Store a Mini in its task issue body. For a single-task trial, use separate Big/Mini sections in the same issue. Keep local IDs and resulting Linear IDs/URLs mapped in checkpoints.
4. Preserve unrelated user content when editing. Prefer an anchored partial edit — the official MCP's `patch` applies edits in order and atomically, and requires each anchor string to match the current content exactly once, so a concurrent change fails the save instead of being silently overwritten. This is what the `do-the-thing: BIG-001` marker is for: it is the anchor. Without partial editing, read the latest body immediately before writing and replace the whole field, knowing that anything written between your read and your write is lost.
5. Put material questions where they can be answered and tracked. A comment on the issue is the right surface when the host can write comments, and a threaded reply keeps one question's answers together. Record the responder and the decision; an unrelated comment does not resolve a question. Without comment writing, keep questions and answers in the Big's interview table and say so — do not spread them across issue descriptions where the next session cannot find them.
6. Before creating child issues, inspect existing children and dependencies. Create only the authorized scope. Link a Mini to its Big through a parent reference when the host supports one, otherwise group them under a shared project. After each mutation, read back its ID, parent relationship, body, and status as relevant. If the response is uncertain, reconcile before retrying; do not promise exactly-once delivery.
7. Select statuses from the team's actual configured states. Never hard-code a status UUID or equate an agent session ending with a completed issue.
8. Record failed or incomplete synchronization explicitly. Keep a local checkpoint until remote results are verified. Do not place credentials or private source contents in public examples.

Some hosts route writes through a gateway with its own rules — a required label, a language or length limit, a scan that refuses secrets or personal data. Those constraints are the host's, not this skill's; satisfy them and record in the checkpoint that you did. If a constraint blocks content the work genuinely needs, that is a blocker to report, not something to work around by switching to an unguarded path.

For implementations that add a background service later, consult current official API documentation for OAuth, webhooks, signatures, activities, and signals. This package does not implement those capabilities.
