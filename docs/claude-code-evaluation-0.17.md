# v0.17 Claude Code 터미널 평가

평가일: 2026-09-13. 실제 Claude Code 2.1.263의 `-p` 실행이며 초기화 로그의 모델은 `claude-sonnet-5`였다. Codex의 가상 판단 응답으로 대체하지 않았다.

## 환경과 범위

v0.17 후보의 `skills/do-the-thing` 폴더를 독립된 합성 시험 프로젝트 `.claude/skills/`에 복사했다. 용어 사례 1회와 구현 사례 3회(초기·실패한 low effort·최종)를 실행했다. `/do-the-thing`을 진입 명령으로 사용했다. 프로젝트 설정만 사용하고 훅과 MCP를 제외했다. 읽기·쓰기·터미널 도구를 시험 범위에 맞게 제공했으며, 외부 발신·배포·실데이터 접근은 요청하지 않았다. 별도 테스트를 명확히 하기 위한 설정이지, 일반 사용 환경 전체를 대표하는 것은 아니다.

## 시험 1: 모호한 상태의 명세화

기존 용어집은 `canceled`(주문 이행 취소)와 `refunded`(환불 완료)를 구분했다. 사용자 입력은 두 상태를 하나의 완료 상태로 합치고 싶다는 요구이며 구현은 금지했다.

실제 읽기 기록에서 `domain-modeling.md`와 `interview.md`를 확인했다. Claude는 Q-01 한 개로 통합 상태의 의미를 질문하고 답변을 기다리며 종료했다. 승인된 용어를 임의 변경하거나 명세를 확정·구현하지 않았다. CLI는 성공 종료했고 도구 승인 거부는 없었다. 후속 사용자 답변 이후의 명세 작성은 이 시험에서 실행하지 않았다.

## 시험 2: 승인된 명세의 구현과 테스트 증명

승인 명세 BIG-17 rev1은 CSV 정산 CLI에서 paid만 합산, canceled/refunded 제외, 상태와 관계없이 중복 id 거부(종료코드 2·stderr·성공 stdout 없음), subprocess 검증을 요구했다. 기존 구현은 모든 상태를 합산하고 중복을 허용했다. 초기 테스트는 빈 입력만 검사하여 결함이 있어도 1개가 통과했다. 체크포인트는 의도적으로 손상시켰다.

Claude는 실제로 `summary.py`를 수정하고 기존 `test_summary.py`를 보강했다. 테스트 증명 내부 지침을 읽었으며, 정상 실행에서 7개 테스트가 통과했다. 격리된 임시 사본에서 시행한 변이는 다음과 같다.

| 변이 | 실행한 테스트 | 실제 결과 |
|---|---:|---|
| 중복 id 가드 제거 | 7 | 관련 테스트 2개 실패 |
| paid 필터 제거 | 7 | 관련 테스트 4개 실패 |
| 중복 오류를 성공 종료로 삼킴 | 7 | 관련 CLI 테스트 1개 실패 |

세 변이 모두 문법 오류나 수집 0건이 아니라 해당 동작을 확인하는 테스트 실패였다. 중간에 `unittest`의 `discover` 없는 `-s/-p` 옵션 사용으로 명령 오류가 한 번 발생했고, Claude는 올바른 명령으로 원본의 7개 테스트를 재실행해 통과했다. 실패한 명령 자체를 검증 성공으로 세지 않는다.

별도 검증자는 혼합 상태·paid 없음·빈 입력·paid 중복·서로 다른 상태의 중복 등 5개 CLI 사례를 독립적으로 실행해 기대 출력과 종료코드를 확인했다. 승인 명세와 손상 체크포인트의 초기 SHA256도 유지됐다.

## 해석의 한계

첫 구현 실행은 AC와 저장소 규칙을 자체 확인했으나 `references/code-review.md` 읽기 호출이 없었다. 내부 역할의 자동 진입이 완전했다고 보지 않는다. 그래서 step 5의 완료 직전에 리뷰 계약을 읽고 두 축을 따로 기록하도록 명시했다.

두 번째 실행(low effort)은 7개 테스트가 통과했지만 **스킬 준수 실패**로 분류했다. 테스트/리뷰 내부 계약을 읽지 않았고, 원본 구현을 잠시 이전 버전·변이로 교체한 뒤 복원했으며, 손상된 `checkpoint.json`을 `.damaged`로 옮기고 같은 경로에 새 파일을 만들었다. 원본 보존과 격리 조건을 충족하지 않는다. 실제 데이터 대신 disposable fixture였으므로 사용자 프로젝트는 영향받지 않았다. 이 실행의 성공 종료·자체 완료 보고는 합격 증거가 아니다.

이를 반영해 step 4에 테스트 작성 전 계약 읽기와 별도 디렉터리 변이 실행을, step 6에 손상 기록의 경로·바이트 보존(이동·이름 변경 금지)을 명시했다. 첫·세 번째는 기본 effort, 두 번째는 low effort로 설정이 달라 개선율을 계산하지 않는다.

## 최종 후보 재시험

같은 초기 코드·명세·손상 기록으로 만든 세 번째 fixture에서 기본 effort로 재실행했다. 실제 읽기 로그에 `test-proof.md`와 `code-review.md`가 모두 나타났다. 7개 테스트가 통과했고, 별도 임시 디렉터리에 복사한 소스와 테스트에서만 변이를 적용·복원했다.

| 최종 변이 | 테스트 수 | 실패 수 |
|---|---:|---:|
| paid 필터 제거 | 7 | 4 |
| 중복 id 감지 제거 | 7 | 2 |
| 중복 오류 종료코드 2를 0으로 변경 | 7 | 1 |
| 중복 오류에서도 성공 JSON 출력 | 7 | 1 |

별도 검증자의 CLI 5개 사례가 모두 통과했다. SPEC.md와 checkpoint.json의 원래 경로·SHA256이 유지됨을 확인했다. 이 결과는 보강 후 기본 effort 실행 한 번의 관측이며 low effort의 안정성까지 확인한 것은 아니다.

최종 실행은 234.365초·34턴으로 정상 종료했고 도구 승인 거부는 없었다. `EVIDENCE.md`에 Spec/Standards 검토를 따로 기록하고, `checkpoint_recovery.md`를 별도로 작성했다. `completion_record.json`의 구조 검증도 통과했다. 종료 후 별도 검증자가 테스트 7개와 CLI 5개 사례, 원본 해시를 다시 확인했다. 이 완료 판정은 Claude의 자체 요약만을 근거로 삼지 않는다.

이 결과는 두 개의 합성 로컬 사례와 한 모델 종류에 한정된다. 자동 발견률, 다른 Claude 계정·설정, 모든 업무에서의 안정성, 실제 Linear 복구·O’Reilly 검색/본문 열람·배포 성공을 입증하지 않는다. O’Reilly는 이 정산 작업에서 필요한 지식 공백이 없고 MCP도 제외했으므로 호출하지 않았다. 기존 저장소의 40개 테스트와 23개 변이 검사는 스킬 내부 검증기의 검사이며, fixture의 7개 테스트와 초기 3개·최종 4개 변이는 별개다.
